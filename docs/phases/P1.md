# P1 — LLM Gateway + cấu hình provider (M12)

| Ước lượng | Phụ thuộc | Nhánh |
| --- | --- | --- |
| 1,5 tuần | PG, PU | `feat/p1-llm-gateway` |

**Mục tiêu:** không còn chỗ nào gọi thẳng OpenAI; đổi provider/model theo tác vụ trên UI mà không khởi động lại.

## Lát việc

**L1. Gateway LLM trong Go**
- [ ] `internal/llm`: `chat`, `stream`, `structured(json_schema)`, `embed`; tham số `task`; dùng `openai-go`
- [ ] Registry provider: mỗi provider là một **base URL tương thích OpenAI + key riêng** (D46); thêm provider = thêm một dòng cấu hình, không thêm code
- [ ] Map lỗi 429 / timeout / auth về một kiểu lỗi chung để lớp retry (backoff luỹ thừa + jitter) không phải biết đang nói chuyện với provider nào
- [ ] Chuỗi fallback theo `llm_task_routes.fallback_order`
- [ ] Ghi `llm_audit` mỗi lời gọi, kèm `trace_id` OpenTelemetry
- [ ] Đường nóng hỏi–đáp tuân thủ **D47**: đúng MỘT lời gọi sinh chữ cho mỗi câu hỏi, luôn có stream; không LLM viết lại câu hỏi, không LLM rerank hay tổng hợp trên đường nóng

**L1b. LLM Scheduler** (đọc `SYSTEM_DESIGN.md` mục 3.1 — đây là thành phần quyết định hệ thống có chịu được tải hay không)
- [ ] `internal/llm/scheduler`: ba làn `INTERACTIVE` / `NEAR_REALTIME` / `BATCH`; mỗi `task` ánh xạ cố định vào một làn
- [ ] Token bucket RPM + TPM theo model (số liệu từ `llm_models`), trạng thái trên Redis để nhiều bản gateway và worker dùng chung; semaphore `LLM_MAX_CONCURRENCY`
- [ ] Làn BATCH tối đa `LLM_BATCH_SHARE` hạn mức khi làn INTERACTIVE có việc chờ
- [ ] Hàng chờ INTERACTIVE giới hạn `LLM_QUEUE_MAX`; đầy → lỗi `OVERLOADED` kèm `retry_after` ước tính (gateway trả 503)
- [ ] Cầu dao theo provider (mở 30 s sau N lỗi/429 liên tiếp) → fallback; retry backoff luỹ thừa + jitter
- [ ] Deadline lấy từ `context.Context` của request HTTP; client huỷ → huỷ luôn lời gọi provider
- [ ] Suy giảm: mọi provider chết → trả lời trích xuất từ chunk + cờ `degraded=true`
- [ ] Khử trùng yêu cầu giống hệt đang bay (single-flight theo hash prompt) cho làn không cá nhân
- [ ] **Trần ngân sách** (`llm_budgets`, theo ngày / tháng, toàn hệ thống và theo lớp): bộ đếm chi phí trên Redis cập nhật sau mỗi lời gọi; 80% → sự kiện cảnh báo; 100% → làn BATCH ngừng nhận việc mới (việc nằm lại hàng đợi), làn INTERACTIVE chuyển sang model rẻ nhất đã cấu hình; không bao giờ tắt chat trong im lặng
- [ ] Provider giả `fake`: độ trễ và tỷ lệ lỗi cấu hình được (dùng cho test tải và CI) + **chế độ replay** phát lại response đã ghi, để test hợp đồng từng provider mà không tốn tiền
- [ ] **Test hợp đồng cho MỖI provider** đối chiếu với provider `fake`: cùng `json_schema` thì kết quả `structured()` phải cùng hình dạng. D46 đã lường trước rằng structured output qua lớp tương thích OpenAI của vài provider yếu hơn bản gốc — provider nào không đạt thì ghi rõ và không gán cho tác vụ cần schema

**L2. Không SDK provider nào nằm ngoài `internal/llm`**
- [ ] Rà cả `backend-go`: mọi lời gọi sinh chữ và embedding đều đi qua `internal/llm`; không gói nào khác import SDK provider trực tiếp (có test kiến trúc / cổng grep trong CI)
- [ ] Test của các gói khác dùng provider `fake` của gateway, không tự chế client giả
- [ ] Embedding: khoá 1536 chiều; từ chối model khác chiều

**L3. Cấu hình phía Go**
- [ ] Migration llm_config; `internal/llmconfig` CRUD; AES-GCM (`platform/crypto`); key chỉ ghi, trả về dạng che
- [ ] `POST …/test` gọi thẳng `internal/llm` với provider vừa nhập (không lưu nếu hỏng)
- [ ] Sau khi lưu: nạp lại registry ngay trong tiến trình (một tiến trình Go, không cần báo cho ai khác); biến môi trường làm dự phòng khi bảng trống

**L4. Frontend**
- [ ] `/settings/llm` (`design/DESIGN.md` §14.23, `LLMRouteTable`): bốn phần theo thứ tự — kết nối provider, bảng gán tác vụ, chuỗi fallback, cấu hình embedding tách riêng vì đổi là phải re-index; key chỉ ghi, sau khi lưu chỉ hiện trạng thái đã kết nối; trường nâng cao nằm sau `Cài đặt nâng cao`; nút Test là hành động phụ trên từng dòng; bảng usage (token, chi phí ước tính, độ trễ, lỗi theo tác vụ)

## Cổng nghiệm thu
```bash
grep -rn "openai\.\|anthropic\.\|genai\." backend-go --include=*.go | grep -v "internal/llm/" ; test $? -eq 1
cd backend-go && go test -race ./internal/llm/...
cd backend-go && go test -race ./internal/llm/scheduler/...   # BATCH không làm INTERACTIVE chờ quá ngưỡng; hàng đầy → OVERLOADED; cầu dao mở/đóng; huỷ deadline dừng lời gọi
cd backend-go && go test ./internal/llm -run TestProviderContract -v   # mỗi provider khớp hình dạng của provider fake
cd backend-go && go test -race ./internal/llmconfig/... ./internal/platform/...
make eval                                    # script đánh giá offline trong benchmarks/ gọi qua HTTP API
```

## Bạn tự kiểm
- Thêm 2 provider thật, đổi CHAT giữa hai cái, chat ngay sau đó; xem `llm_audit` ghi đúng provider.
- Nhập key sai → nút Test báo lỗi rõ; key không bao giờ hiện lại trên UI hay trong log.
- Tắt provider chính → fallback chạy.
- Bơm 200 việc BATCH giả rồi chat: chữ đầu tiên vẫn ra trong SLO.
- Tắt hết provider: chat trả lời kiểu trích xuất kèm nhãn "AI tạm thời không khả dụng", không treo.

## Ghi cho luận văn
Sơ đồ gateway; bảng tác vụ → model; kết quả golden set theo từng provider và ghi chú provider nào yếu ở structured output.
